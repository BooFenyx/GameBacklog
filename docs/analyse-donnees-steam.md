# Données Steam récupérables à la connexion — analyse pour GameBacklog

> Analyse du 30 octobre 2026, mise à jour le 31 octobre 2026. Sources : documentation
> officielle Steamworks, wiki Valve, doc communautaire générée depuis
> `GetSupportedAPIList`, retours d'expérience datés (GitHub, forums Steam, Stack Overflow) et
> **appels réels** aux endpoints publics.
>
> **Conclusion opérationnelle** : avec une clé Web API unique appartenant à l'application,
> Steam ne renvoie **pas** `rtime_last_played` pour les autres comptes, et ce n'est **ni un
> bug de code ni un réglage de confidentialité**. La colonne `last_played_at` a donc été
> **supprimée** de la base (migration `0009`) et le champ `lastPlayedAt` ne figure plus dans
> les réponses de l'API. L'application ne lit plus `rtime_last_played`, **même pour le compte
> propriétaire de la clé** : l'activité affichée est **dérivée** de `playtime_forever`, de
> `playtime_2weeks` et des succès. La suite du document explique la règle, les preuves, ce
> que cela cassait et le modèle d'activité mis en place.

## Décision du 31/10/2026

- `last_played_at` est supprimé de la base, de l'API et de l'interface.
- `rtime_last_played` n'est plus lu, y compris pour le compte propriétaire de la clé : pas de
  branchement conditionnel « si propriétaire ».
- Aucune donnée réservée au propriétaire de la clé n'est utilisée : **mêmes données pour tous**.
- L'activité est dérivée de trois sources accessibles à un tiers :
  - `sync_delta` : hausse de `playtime_forever` entre deux synchronisations datées ;
  - `recent_window` : `playtime_2weeks > 0` ;
  - `achievement` : date du dernier succès débloqué (`unlocked_at`).
- Aucune date exacte de dernière partie n'est affichée : les sources sont des **bornes**
  hautes (`sync_delta`, `recent_window`) ou basses (`achievement`).

## 0. À lire en premier — la limite structurante

### 0.1 La règle

`IPlayerService/GetOwnedGames` ne renvoie la **date de dernière partie** (`rtime_last_played`)
et les **compteurs de temps par plateforme** que si le `steamid` interrogé est celui du
**compte propriétaire de la clé Web API**.

Le wiki Valve le dit explicitement :

> « Private, friends-only, and other privacy settings are not supported unless you are asking
> for your own personal details (ie the WebAPI key you are using is linked to the steamid you
> are requesting). »
> — <https://developer.valvesoftware.com/wiki/Steam_Web_API#GetOwnedGames_.28v0001.29>

GameBacklog utilise **une seule clé** (`STEAM_API_KEY`, côté API) pour servir tous ses
utilisateurs. Chaque utilisateur connecté est donc, du point de vue de Steam, un **tiers**.
Conséquence : les champs « riches » sont **absents de la réponse** (pas mis à `0`, pas mis à
`null` : absents), et le mapping actuel les transforme en `null`.

### 0.2 Preuves datées

| Date | Source | Constat |
|---|---|---|
| 2016-2017 | Stack Overflow 38042998 | La date exacte n'est pas dans l'API ; elle est dans `localconfig.vdf` (`"LastPlayed" "1466894369"`), ou dans la variable JS `rgGames` de la page Communauté. |
| 2023-03-09 | Stack Overflow 75693044 | `rtime_last_played` apparaît dans l'API officielle… mais l'appel utilise `access_token` (session du compte). La variable `rgGames` a été retirée par Valve le même mois. |
| 2023-08-17 | GitHub `alifeee/steam_collage_api#20` | Comparaison de charges utiles : **compte de la clé** → `playtime_windows_forever`, `playtime_mac_forever`, `playtime_linux_forever`, `rtime_last_played`, `playtime_disconnected` ; **autre compte** → seulement `appid`, `name`, `playtime_2weeks` (si récent), `playtime_forever`, `img_icon_url`, `has_community_visible_stats`. |
| 2024-04-23 | Forum Steam 4361249282371665215 | « this field is only accessible when using the API key generated by the user whose data I'm fetching » ; pour un autre compte, « the API only returns two fields: appid and playtime_forever ». |
| 2025-09-22 | Commentaire Stack Overflow 140751666 | « i only get rtime_last_played for the profile linked to the Api Key, all other profiles have not this field at all (even a public profile with all privacy settings turned off) ». |
| 2026-10-30 | Tests GameBacklog | `GetPlayerSummaries` et `GetSchemaForGame` sans clé → **400** ; `GetRecentlyPlayedGames` sans clé → **403** ; `GetWishlist` sans clé → **200 `{}`** ; `appdetails` avec deux AppID → **400** ; page Communauté `?xml=1` → **page de connexion** (XML déprécié). |

La restriction n'est donc **pas** une question de profil public/privé : elle s'applique même
avec toutes les options de confidentialité ouvertes. Elle n'est pas non plus détectable par un
code HTTP : la réponse est un `200` avec un objet plus pauvre.

### 0.3 Matrice des champs de `GetOwnedGames`

| Champ | Clé du compte | Clé tierce (notre cas) | Fiabilité |
|---|---|---|---|
| `appid` | ✅ | ✅ | certaine |
| `name` (avec `include_appinfo`) | ✅ | ✅ | certaine |
| `img_icon_url`, `img_logo_url` | ✅ | ✅ | certaine |
| `playtime_forever` | ✅ | ✅ | certaine |
| `playtime_2weeks` | ✅ | ✅ présent quand le jeu a été joué dans les 14 jours ; omis sinon | **vérifié le 31/10/2026 pour un tiers** (Squad `119`, Eden Crafters `1372`) |
| `has_community_visible_stats` | ✅ | ✅ | certaine |
| `rtime_last_played` | ✅ | ❌ **absent** | certaine (3 sources indépendantes) ; **non utilisé par GameBacklog** |
| `playtime_windows_forever`, `playtime_mac_forever`, `playtime_linux_forever`, `playtime_deck_forever` | ✅ | ❌ **absents** | observé en 2023, cohérent avec 2024 |
| `playtime_disconnected` | ✅ | ❌ **absent** | observé en 2023 |
| `content_descriptorids` | ✅ | ❓ | non vérifié pour un tiers |
| `family_shared` (`include_family_licenses`) | ✅ | ❓ | non vérifié pour un tiers |
| `capsule`, `sortas`, `capabilities` (`include_extended_appinfo`) | ✅ | ❓ | non vérifié pour un tiers |

**Ne pas confondre** : `playtime_2weeks` (minutes sur 14 jours) n'est pas `rtime_last_played`
(timestamp de la dernière partie). Le premier peut exister sans le second.

### 0.4 Ce que cela cassait avant le lot du 31/10/2026

> Ce tableau est un **historique** de l'état avant correction, conservé pour comprendre
> l'origine du problème. Il ne décrit plus le code actuel.

| Emplacement | Symptôme | Cause |
|---|---|---|
| `api/src/library/library.service.ts:93` et `:268` | `playtimeLast2Weeks` toujours `0` | le code lit `playtime_last_2_weeks`, alors que Steam renvoie `playtime_2weeks` |
| `api/src/library/library.service.ts:269-271` | `lastPlayedAt` toujours `null` | `rtime_last_played` absent pour un tiers |
| `api/src/library/library.service.ts:216-217` | le tri `recent` retombait silencieusement sur l'ordre alphabétique | `ORDER BY last_played_at DESC NULLS LAST` avec 100 % de `NULL` |
| `api/src/sync/sync.service.ts:302` et `:309` | la colonne `last_played_at` était écrasée par `null` à chaque sync | même cause |
| `api/src/db/schema.ts:123` | colonne `last_played_at` inutilisable en pratique | alimentée uniquement par un champ absent |
| page `/jeu/:appId` | « Dernière partie : — » pour tous les jeux | idem |
| filtres « Steam Deck » / par OS | impossibles | `playtime_deck_forever` et `playtime_*_forever` absents |

Deux bugs **indépendants** se cumulaient donc :

1. **Nom de champ erroné** (`playtime_2weeks`) → les minutes des 2 dernières semaines étaient
   perdues même si Steam les renvoyait.
2. **Champ interdit aux tiers** (`rtime_last_played`) → la date exacte était définitivement
   indisponible avec une clé d'application.

État après le lot : le code lit `playtime_2weeks`, la colonne `last_played_at` a été
supprimée (`0009`), `rtime_last_played` n'est plus lu et le tri `recent` s'appuie sur
`last_activity_at DESC NULLS LAST, playtime_last_2_weeks DESC`.

### 0.5 Ce que cela ne casse pas

- `playtime_forever` (temps total) : fiable, cœur du backlog.
- La bibliothèque, les genres, catégories, modes, support manette (`appdetails`).
- Les succès : schéma (`GetSchemaForGame`) et progression (`GetPlayerAchievements`) si le
  profil est public.
- La recherche vectorielle, les filtres, les facettes, la wishlist.
- Le tri par nom et par temps de jeu.
- `GetRecentlyPlayedGames` (si le profil est public) : donne l'**ensemble** des jeux joués
  dans les 14 derniers jours, sans date exacte.

### 0.6 Les fausses pistes (à ne pas implémenter)

| Piste | Pourquoi c'est non |
|---|---|
| **Demander à chaque utilisateur sa propre clé Web API** | Les CGU Steam interdisent de partager sa clé : « You agree to keep your Steam Web API key confidential, and not to share it with any third party » et « You may not transfer, assign, or delegate […] your Steam Web API key to any third party » (<https://steamcommunity.com/dev/apiterms>). Stocker des clés utilisateurs, c'est héberger un secret qui ne nous appartient pas, avec révocation, support et risque juridique. **À rejeter explicitement.** |
| **Demander le cookie `steamLoginSecure` ou un `access_token`** | C'est un secret de session complet (prise de contrôle du compte). Jamais. |
| **Scraper `steamcommunity.com/.../games`** | La variable `rgGames` a été retirée en mars 2023 ; le XML communautaire est déprécié et, testé le 30/10/2026, renvoie une page de connexion. Fragile et contraire à l'esprit des CGU. |
| **Utiliser une API tierce (SteamDB, SteamAPI.io…)** | Elle est soumise à la même restriction amont, ajoute un coût, une dépendance et ses propres CGU. |
| **`GetSingleGamePlaytime`** | La clé doit être associée à l'AppID (clé éditeur) : inutilisable pour un catalogue tiers. |
| **`GetRecentlyPlayedGames` comme remplacement** | Ne donne que la fenêtre de 14 jours, sans date. Utile comme **signal**, pas comme date. |
| **Lire `localconfig.vdf`** | Donne la date exacte (`LastPlayed`), mais uniquement sur la machine du joueur : hors périmètre d'une web app. Option possible pour un futur compagnon desktop, pas pour la version actuelle. |

## 1. Ce que « se connecter » donne réellement

### 1.1 OpenID 2.0 — l'identité seule

| | Détail |
|---|---|
| Endpoint | `https://steamcommunity.com/openid/login` (OpenID 2.0, pas OIDC) |
| Ce qu'on obtient | le `claimed_id` `http://steamcommunity.com/openid/id/<steamid64>` |
| Ce qu'on n'obtient pas | e-mail, pseudo, avatar, bibliothèque, « scopes » |
| Profil privé | la connexion fonctionne quand même ; seules les lectures de données échoueront |
| Vérification | rejouer la réponse en `check_authentication` (`openid.mode=id_res`) |

« Se connecter » = obtenir un SteamID64 stable. Tout le reste vient des appels suivants, avec
la limite du § 0.

### 1.2 La clé Web API

- Créée sur `https://steamcommunity.com/dev/apikey`, associée à un **nom de domaine**.
- Reste **côté serveur**.
- N'est **pas** liée au joueur connecté : c'est un accès aux données publiques, avec les
  restrictions du § 0.
- Quota : **100 000 appels/jour** (CGU).

### 1.3 Matrice de confidentialité

| Réglage Steam | Effet observable |
|---|---|
| Profil « Privé » | `communityvisibilitystate = 1` ; `GetOwnedGames` renvoie `{}` |
| Profil « Amis uniquement » | idem pour un tiers non ami |
| Profil public + **Détails de jeu : Privé** | `GetOwnedGames` renvoie `{"response":{}}` (HTTP 200) |
| Profil public + détails publics + **temps total privé** | jeux listés, `playtime_forever` à 0 |
| Succès masqués | `GetPlayerAchievements` → `success:false` |
| Liste d'amis privée | `GetFriendList` → 401 |
| Wishlist privée | `GetWishlist` → `{"response":{}}` |

À distinguer de la limite du § 0 : ici, c'est l'utilisateur qui restreint ; là, c'est Steam qui
restreint l'appelant. Les deux produisent parfois un objet vide, mais pas au même endroit :
la confidentialité vide **toute** la réponse, la limite de clé retire **certains champs**.

### 2.2 Bibliothèque (`IPlayerService/GetOwnedGames/v1`)

**Paramètres** :

| Paramètre | Effet | Intérêt pour un tiers |
|---|---|---|
| `include_appinfo` | ajoute `name`, icônes, stats visibles | ✅ |
| `include_played_free_games` | inclut les free-to-play **joués** | ✅ |
| `include_free_sub` | inclut les jeux du « free sub » | ✅ |
| `skip_unvetted_apps=0` | inclut les jeux « Profile Features Limited » (non documenté) | ✅ |
| `include_extended_appinfo` | ajoute `capsule`, `sortas`, `capabilities` | ❓ à vérifier |
| `include_family_licenses` | ajoute les jeux joués via le partage familial (`family_shared`) | ❓ à vérifier |
| `include_all_free_games` | tous les free-to-play, même non lancés | ✅ |
| `language` | langue des `appinfo` | ✅ |
| `appids_filter` | restreint à une liste d'AppID (via `input_json`) | ✅ |

**Champs de réponse** : voir la matrice du § 0.3. Les seuls champs fiables pour un tiers sont
`appid`, `name`, `img_icon_url`, `img_logo_url`, `playtime_forever`,
`has_community_visible_stats`, et éventuellement `playtime_2weeks`.

> `GetOwnedGames` ne renvoie **ni prix, ni date d'achat, ni date d'ajout**. Et pour un tiers,
> il ne renvoie **pas** la date de dernière partie. Seul `playtime_forever == 0` permet
> d'affirmer « jamais lancé ».

### 2.3 Activité récente

| Endpoint | Clé | Données | Limite |
|---|---|---|---|
| `IPlayerService/GetRecentlyPlayedGames/v1` | oui | `total_count` + jeux des 2 dernières semaines (`playtime_2weeks`, `playtime_forever`) | fenêtre de 14 jours, **aucune date** |
| `IPlayerService/GetSingleGamePlaytime/v1` | oui, **liée à l'AppID** | temps d'un jeu | inutilisable pour un catalogue tiers |
| `IPlayerService/IsPlayingSharedGame/v1` | oui | jeu emprunté en cours | — |
| `ISteamUserStats/GetNumberOfCurrentPlayers/v1` | non (vérifié) | joueurs actifs maintenant | — |

`GetRecentlyPlayedGames` est le **meilleur signal de récence disponible pour un tiers** : un
appel, l'ensemble des jeux joués depuis 14 jours. Il ne dit pas *quand* précisément.

### 2.4 Succès et statistiques

| Endpoint | Clé | Réponse | Tiers |
|---|---|---|---|
| `ISteamUserStats/GetSchemaForGame/v2` | oui | `availableGameStats.achievements[]` (`name`, `displayName`, `description`, `hidden`, `icon`, `icongray`), `stats[]` | ✅ |
| `ISteamUserStats/GetPlayerAchievements/v1` | oui | `playerstats.success`, `achievements[]` (`apiname`, `achieved`, `unlocktime`, `name`, `description`) | ✅ si profil public |
| `ISteamUserStats/GetUserStatsForGame/v2` | oui | valeurs de stats du joueur | ✅ si public |
| `ISteamUserStats/GetGlobalAchievementPercentagesForApp/v2` | non (vérifié) | `{name, percent}` | ✅ |

`unlocktime` est un timestamp exact. C'est la **seule date exacte par jeu** accessible pour un
tiers — mais elle date le dernier **succès**, pas la dernière **partie**. À utiliser comme
borne inférieure, pas comme vérité.

Cas particulier : jeu sans succès → `{"playerstats":{"success":false,"error":"Requested app has no stats"}}`.

### 2.7 Ce qui n'est **pas** exposé

- prix payé, date d'achat, remises historiques, remboursements ;
- historique de sessions (date + durée) ;
- temps de jeu par jour/semaine au-delà des 2 dernières semaines ;
- **date exacte de dernière partie pour un tiers** ;
- temps par OS / Steam Deck pour un tiers ;
- clés produit, provenance de licence, jeux retirés ;
- succès d'un jeu non possédé ;
- durée HowLongToBeat (service tiers) ;
- notes personnelles / tags utilisateur.

## 3. Métriques de « backlog » calculables

| Métrique | Formule / source | Disponible pour un tiers ? |
|---|---|---|
| Taille de la bibliothèque | `COUNT(library_entries)` | ✅ |
| Jeux jamais lancés | `playtime_forever = 0` | ✅ |
| % de backlog | jamais lancés / total | ✅ |
| Heures dormantes | somme des `playtime_forever` des jeux « en cours » | ✅ |
| Temps par genre / mode / manette | agrégation `genres`, `category_ids`, `controller_support` | ✅ |
| Dernière activité exacte | `rtime_last_played` | ❌ |
| Jeux joués dans les 14 jours | `playtime_2weeks > 0` ou `GetRecentlyPlayedGames` | ⚠️ |
| Récence approchée | delta de `playtime_forever` entre deux syncs | ✅ (à partir de la 2ᵉ sync) |
| Borne basse par succès | `MAX(unlocktime)` | ✅ si succès publics |
| Proches de mes goûts | distance pgvector entre embeddings | ✅ |
| Répartition Deck / OS | `playtime_deck_forever`, `playtime_*_forever` | ❌ |
| Valeur « au prix actuel » | somme des `price_overview.final` | ✅ |
| Progression succès | `achievements_unlocked / achievements_total` | ✅ |
| Wishlist vs bibliothèque | `GetWishlist` − `GetOwnedGames` | ✅ |

## 4. Contraintes opérationnelles

| Contrainte | Valeur | Conséquence |
|---|---|---|
| Quota clé | **100 000 appels/jour** | ~500 jeux × 2 appels succès = 1 000 : OK, mais à étaler |
| `appdetails` | ~**200 requêtes / 5 min** (communauté) | 500 fiches ≈ 13 min minimum ; mettre en file |
| Rate limit par méthode | non documenté | prévoir 429 + `Retry-After` |
| Codes | 400 paramètre/clé, 401 clé invalide, 403 droit refusé, 429 quota | ne pas confondre avec « profil privé » (200 + vide) |
| `x-eresult` | 25 `LimitExceeded`, 84 `RateLimitExceeded` | journaliser |
| `appdetails` | **1 AppID par requête** (vérifié 30/10/2026) | pas de batch |
| XML communautaire | déprécié, renvoie une page de connexion (vérifié) | ne pas s'appuyer dessus |

Ordre de coût croissant à la connexion : profil (1) → bibliothèque (1) → wishlist (1) →
récent (1) → fiches manquantes (1/jeu) → schémas (1/jeu) → progressions (1/jeu).

## 5. Ce que font les backlogs en ligne (benchmark)

| Service | Données exploitées | Apport | Limite |
|---|---|---|---|
| **SteamDB Calculator** | `GetOwnedGames` + prix Store + `appdetails` | valeur du compte, jeux non joués, heures | la date de dernière partie n'est exacte que pour le compte connecté |
| **Backloggd** | saisie manuelle + import | collection multi-plateformes, notes, listes, social | pas de données Steam temps réel |
| **Infinite Backlog** | import + saisie | défis, progression, communauté | idem |
| **Completionist.me / Exophase / Astats / Steam Hunters** | schéma + succès Steam | completion, rareté, historique | centré succès, pas sur le choix du prochain jeu |
| **GG.deals** | wishlist + prix | alertes de promo | pas de bibliothèque |
| **Unalia / Steam Backlog Helper** | bibliothèque + préférences | suggestion de prochain jeu | heuristiques ou LLM, pas de filtres fins |
| **HowLongToBeat** | base collaborative | durée estimée | hors Steam |

**Positionnement de GameBacklog** : la différenciation n'est ni le prix ni la durée estimée,
mais **« quel jeu de MA bibliothèque correspond à ce que je ressens maintenant »** —
recherche sémantique locale + filtres stricts + données possédées. La limite du § 0 ne touche
pas ce cœur de valeur ; elle touche la **récence**, qu'il faut traiter honnêtement.

## 6. Modèle d'activité implémenté (31/10/2026)

### 6.1 Corrections de mapping (faites)

1. `GetOwnedGames` est lu via `playtime_2weeks` (et non `playtime_last_2_weeks`).
2. `rtime_last_played` n'est ni lu ni mappé : le champ a disparu de
   `GetOwnedGamesResponse`.
3. La manette est déduite des ids de catégories Steam `18`/`28`, pas des libellés traduits.
4. `header_image` est validée `http(s)` comme les autres URL.

### 6.2 Modèle de données implémenté (migration `0009`)

```sql
ALTER TABLE library_entries
  ADD COLUMN last_activity_at      timestamptz,
  ADD COLUMN last_activity_source  text,   -- sync_delta | recent_window | achievement
  ADD COLUMN last_activity_precision text, -- upper_bound | lower_bound
  ADD COLUMN last_seen_at          timestamptz;

ALTER TABLE library_entries DROP COLUMN last_played_at;
```

- `last_activity_at` : estimation utilisée pour trier et afficher, **jamais** une date exacte.
- `last_activity_source` : `sync_delta`, `recent_window` ou `achievement` ; la valeur `steam`
  n'existe plus.
- `last_activity_precision` : `upper_bound` ou `lower_bound` ; la valeur `exact` n'existe
  plus.
- `last_seen_at` : horodatage de la dernière synchronisation réussie, point de départ du
  prochain `sync_delta`. Reste `NULL` après la migration pour déclencher une re-sync.
- Index : `library_entries_user_last_activity_idx` sur
  `(user_id, last_activity_at DESC NULLS LAST)` ; l'ancien index `last_played_at` est
  supprimé.

### 6.3 Algorithme de dérivation (`api/src/sync/activite.ts`)

À chaque synchronisation, pour chaque jeu, `deriverActivite` reçoit l'observation Steam, la
ligne précédente et le dernier succès connu :

```ts
const source = precedent?.lastActivitySource ?? null;

// 1. Le temps de jeu a augmenté depuis une sync datée → le jeu a été lancé.
if (precedent?.lastSeenAt && observation.playtimeForever > precedent.playtimeForever) {
  return { at: maintenant, source: 'sync_delta', precision: 'upper_bound' };
}

// 2. Le jeu est dans la fenêtre de 14 jours.
if (observation.playtime2Weeks > 0) {
  if (source === 'sync_delta') return null; // plus précis, on conserve
  return { at: maintenant, source: 'recent_window', precision: 'upper_bound' };
}

// 3. Dernier succès : borne basse, jamais une date de partie.
if (dernierSuccesAt) {
  if (source === 'sync_delta' || source === 'recent_window') return null;
  if (precedent?.lastActivityAt && dernierSuccesAt <= precedent.lastActivityAt) return null;
  return { at: dernierSuccesAt, source: 'achievement', precision: 'lower_bound' };
}

// Aucun candidat : conserver l'existant (ne jamais écrire NULL).
return null;
```

Règles importantes :

- **Pas de `sync_delta` sans `last_seen_at`** : à la première synchronisation, aucun historique
  n'est inventé.
- **Pas de `sync_delta` si `playtime_forever` baisse ou reste égal** (remboursement, partage
  familial, correction).
- `sync_delta` n'est **jamais** écrasé par `recent_window` ou `achievement`, sources moins
  précises.
- `achievement` ne remplace ni `sync_delta`/`recent_window`, ni un succès plus récent.
- Un candidat `null` n'écrit **jamais** `NULL` dans les colonnes d'activité : les champs sont
  omis du `set`.
- `last_seen_at` est mis à jour **après** la boucle, en une requête, jamais avant.
- `unlocked_at` est un `timestamp` sans fuseau qui stocke un mur UTC : le passage vers
  `timestamptz` exige `AT TIME ZONE 'UTC'` (voir `marquerActiviteSucces`).

### 6.4 API et UI

- `GET /api/library`, `GET /api/games/:appId` et `GET /api/search` renvoient
  `lastActivityAt`, `lastActivitySource` et `lastActivityPrecision` ; `lastPlayedAt` est
  absent.
- `GET /api/library/facets` renvoie `lastActivityDisponible`, faux quand aucune entrée n'a
  d'activité (le tri « Activité récente » est alors masqué).
- `releaseDate` est renvoyé en `YYYY-MM-DD`.
- Tri `tri=recent` : `ORDER BY last_activity_at DESC NULLS LAST, playtime_last_2_weeks DESC,
  lower(name)`.
- Affichage selon la source :

  | Source | Libellé |
  |---|---|
  | `sync_delta` | Joué depuis la dernière synchronisation |
  | `recent_window` | Joué dans les 14 derniers jours (ou « dans les 14 jours avant le <date> » si ancien) |
  | `achievement` | Dernier succès le <date> |
  | `null` | — + infobulle |

- Le badge « Jamais lancé » reste basé **uniquement** sur `playtimeForever === 0`.
- Accueil « à relancer » : `playtime_2weeks > 0` ou `recent_window`, jamais une date exacte.
- Accueil « proches » : `recent_window` / `playtime_2weeks`.
- Ne pas ajouter de filtre « Steam Deck » tant que `playtime_deck_forever` n'est pas vérifié
  pour un tiers.

### 6.5 Tests en place

- Mapping : `playtime_2weeks` bien lu ; un payload contenant `rtime_last_played` ne produit
  aucune propriété `lastPlayedAt`.
- Dérivation : augmentation → `sync_delta` ; valeur égale → pas de changement ; baisse → pas
  de changement.
- `recent_window` : `playtime_2weeks > 0` → source `recent_window`.
- Priorité : `sync_delta` n'est jamais écrasé par `recent_window`/`achievement`.
- Première sync : aucun `sync_delta` (cas `lastSeenAt = null`).
- Tri `recent` : le jeu avec activité passe avant celui sans activité.
- Facettes : `lastActivityDisponible` vaut `true` dès qu'une entrée a une activité.

### 6.6 Ce qu'il ne faut pas promettre

- « Dernière partie il y a 3 jours » pour un jeu hors fenêtre de 14 jours : impossible.
- « Temps joué sur Steam Deck » : impossible pour un tiers.
- « Historique de sessions » : impossible.
- « Import de la date exacte dès la première connexion » : impossible sans clé utilisateur
  (interdite) ou fichier local (hors périmètre).

### 6.7 Suites à réaccorder (hors lot)

Deux sujets restent ouverts et ne doivent pas être décidés dans ce lot :

- **Accueil intelligent** (« à relancer », « à découvrir », « proches ») : il devra
  s'appuyer uniquement sur `playtime_forever`, `playtime_2weeks` et
  `last_activity_source`. Toute date exacte de dernière partie reste interdite.
- **Amélioration des embeddings** : piste à étudier séparément (texte d'entrée — l'embedding
  actuel utilise `shortDescription`, alors que la spec parle de « description » —,
  régénération après changement de mapping, coût/quota Gemini, version du modèle). Le code
  n'est pas modifié ici.

Règle commune à toute suite : **mêmes données pour tous**, jamais un accès conditionnel aux
champs réservés au propriétaire de la clé.
